# Handling Thumbnail Crawlers & MS Graph API Support

When users open a folder in a file browser like GNOME Nautilus, the browser attempts to generate visual thumbnails for images, videos, and documents. By default, it achieves this by opening every file in the directory and reading the first few megabytes to decode the image header. In a networked FUSE filesystem like OneMount, this standard behavior triggers a "thundering herd" of full-file download requests, saturating the network and local disk.

## Current Support in OneMount
OneMount *does* currently have thumbnail logic built in (`internal/graph/thumbnails.go` and `internal/fs/fuse_thumbnail_handlers.go`). 
- It leverages the Microsoft Graph API's native thumbnail endpoints (`/me/drive/items/{id}/thumbnails/0/{size}/content`).
- It exposes these thumbnails to the FUSE mount via a custom file extension hack. If a user explicitly requests `image.jpg.thumbnail.small`, OneMount intercepts the request and returns the thumbnail payload generated by OneDrive, bypassing the massive file download.

**The catch:** Standard Linux thumbnail crawlers (like Nautilus, Dolphin, or `tumblerd`) do not know about this custom `.thumbnail.small` extension. They will just request `image.jpg`, triggering the massive download bottleneck.

## Recommendations for Improvement

### 1. Implement Extended Attributes (xattrs) for Thumbnails
Linux file browsers and tools often check for Extended Attributes on files. 
- **How:** Expose the OneDrive-provided thumbnails via a specific `xattr`, such as `user.thumbnail` or `xdg.thumbnail`.
- **Benefit:** If thumbnailers on the system are configured to check this attribute, they can extract the preview directly without triggering a read syscall on the file content.

### 2. D-Bus Integration with `org.freedesktop.thumbnails.Thumbnailer1`
Modern Linux desktop environments manage thumbnails through a unified D-Bus service.
- **How:** Create a background daemon or extend OneMount's existing D-Bus service (`internal/fs/dbus.go`) to implement the `org.freedesktop.thumbnails.Thumbnailer1` interface.
- Provide a system-wide configuration that registers `onemount` as the official thumbnail generator for files located in the mount point. 
- When the desktop environment needs a thumbnail, it will ask OneMount over D-Bus instead of reading the file. OneMount can then hit the MS Graph API's lightweight thumbnail endpoints directly and return the image, completely bypassing the FUSE filesystem layer and standard `open()`/`read()` calls.

### 3. File Size & Path Heuristics (The "Fake Header" Approach)
If deep OS integrations are not possible, OneMount can use heuristics within the `Read()` FUSE operation.
- **How:** Identify known thumbnailer process IDs or specific access patterns (e.g., standard sequential reads of exactly `X` bytes at offset 0, followed by a close). 
- If the requested read size is small, OneMount can execute a HTTP `Range` request to the Graph API instead of downloading the whole file, as outlined in the "Large File" recommendations. This allows the thumbnailer to grab the EXIF/header data quickly without triggering an entire gigabyte file download.

### 4. Provide a Custom `thumbnailer` Script
Linux systems use specific configuration files in `/usr/share/thumbnailers/` to define how files are thumbnailed.
- **How:** Ship a `.thumbnailer` configuration file and a lightweight CLI wrapper with OneMount. 
- Configure the system so that whenever it wants a thumbnail for a file on `~/.onemount`, it calls `onemount-thumbnailer %i %o`. This CLI tool simply makes an IPC call to the OneMount daemon, which fetches the MS Graph thumbnail and saves it to the expected output path (`%o`).
